# 系统重点改进方向 TODO

## 文档定位

本文只记录当前已识别、但尚未设计落地的重点改进方向，用于后续排期和逐项深入设计。

优先级排序：1（回测系统）为最高优先级——回测是整个 Agent 系统的 evaluation 环节，速度和质量直接决定后续所有策略迭代的效率；7（界面）优先级最低。2-6 之间暂不排序，彼此也有依赖关系（例如 2 的 benchmark 固化是 1 提速的前提之一；4 选股系统的快速回测能力依赖 1 的部分基础设施）。

---

## 1. 回测系统的整体设计

**现状问题**

回测是这套 Agent 系统最重要的 evaluation 环节，但当前速度很慢，根本原因是：每次跑一个回测交易日，都要重新走一遍极重的"临时数据准备 + 财报基本面分析"链路。财报分析尤其重——它是所有个股分析的基础，但步骤多、耗时长，是当前拖慢回测的最大瓶颈。

**改进方向**

- 理论目标：如果数据都已准备好，回测一天应该只需要约 20 分钟，一天的机器时间不应该只回测一个月，应该能回测更长区间。
- 考虑把整个分析流程（数据准备 → 财报分析 → 多 Agent 辩论决策）用 LangGraph 或其它工作流框架固化下来，替代当前"每天现场重新拼装 Prompt、现场跑一遍完整链路"的方式。
- 长期目标：把单日分析速度压缩到"一天机器时间能跑满一年回测区间"的量级。

**待厘清的开放问题**

- 财报分析这类重步骤能否与"决策当天现场分析"彻底解耦，变成可复用、按公告日期缓存好的静态输入（呼应第 2 点 benchmark 化）？
- 固化到 LangGraph 之后，如何保持现在 Bull/Bear/Juror/finalizer 多 Agent 辩论的角色隔离、唯一写入者、并发批次控制等现有约束？
- 现状参考：`docs/backtest/fixed_tracked_agent_backtest_design.md`、`.codex/skills/backtest-fixed-tracked/`。

## 2. 回测 Benchmark 的构建

**现状问题**

当前每只股票 subagent 的研究包上下文，是由每日宏观新闻、渐进式新闻总结、公告、财报、机构一致预期、各类估值数据、股价数据等共同拼起来的。这些数据大多是"当天现场生成"的产物，而不是固定不变的历史基准数据集。这带来一个根本矛盾：如果宏观总结、渐进式新闻总结这类**依赖当前 Prompt 策略**生成的数据，其生成策略本身发生了变化，历史数据是否需要重新收集？如果不重新收集，回测用的就是"用旧策略生成的输入"，评估结果会失真。

**改进方向（待讨论，非结论）**

- 一种思路：剔除强依赖 Prompt 策略、容易随策略迭代漂移的输入（比如宏观总结、渐进式新闻总结这类"总结型"数据），改用更客观、更稳定的替代数据源：
  - 新闻：改用"财经早餐"一类客观事实播报式新闻，而不是 Agent 生成的主题化总结。
  - 宏观：改用一批客观宏观数据指标（利率、汇率、PMI 等原始数值），而不是宏观总结文本。
- 财报基本面部分如何定基准：若沿用当前已设计好的财报分析方法，其产出数据也是相对固定的（同一份财报、同一套分析方法，理论上可复现），可以考虑把它作为 benchmark 的稳定组成部分。
- 目标是形成一套**版本稳定、可复现**的回测专用高质量 benchmark 数据集，供 LLM 作为固定上下文输入，使得"策略 Prompt 改了"和"数据集本身变了"两件事解耦，回测结果之间才有可比性。

**待厘清的开放问题**

- benchmark 中"客观数据"和"AI 生成总结"的边界具体怎么划？哪些字段必须固定、哪些可以随策略迭代重新生成？
- benchmark 版本化和现有 `data/skill_runs/`、`data/backtests/` 的目录结构如何对接，是否需要新增独立的 benchmark 数据层？

## 3. 跨越式回测系统的设计

**现状问题**

一次回测是否必须把历史区间内的每一个交易日都完整跑一遍？全量逐日回测成本很高，而很多策略改动实际只影响特定场景下的决策。

**改进方向（待讨论，非结论）**

- 针对不同类型的修改点，设计不同粒度的回测方法。例如：如果只改了卖出策略，可以只重点抽样模拟"大跌、历史最高位、大涨"等关键时间节点附近的 LLM 决策，用少量高信息量样本点近似代替全量逐日回测，换取速度。

**待厘清的开放问题**

- 回测节点（采样点）具体如何选择？是按价格/量能的统计特征（如局部极值、异常波动）自动识别，还是按事件（财报、公告）驱动？
- 采样式回测如何与"修改点类型"绑定？换句话说，需要先建立一套"改动分类 → 对应采样策略"的映射规则，而不是每次改动都临时决定测哪几天。
- 采样式回测的结果如何与全量回测的结果做效度校验，确保抽样近似不会系统性高估或低估策略效果？

## 4. 选股系统的设计

**现状问题**

由于个人用户对token的限制，我们无法并发的对几百到几千只股票进行深度分析，所以选股系统决定了整套长期价值投资系统的收益率上限。
但当前设计比较简陋：除了一批人工感兴趣的固定股池外，主要靠几个量化因子的简单组合来筛选股票（详见 `docs/selection_system/因子库与量化初筛系统设计.md`）。另外还有一个已知但暂不适合立即修的小 bug：akshare 的财报接口更新较慢，实际取到的财报数据会比公司真实发布财报公告的时间滞后——由于当前系统已经比较复杂，这类底层数据源改动需要谨慎评估影响面后再动手，不能顺手改。

**改进方向**

- 调研业界成熟的开源选股项目或学术论文中的选股方法，评估能否吸收进当前因子库/量化初筛体系，而不是继续停留在简单因子组合。
- 选股策略本身相对不依赖当前这套"重上下文"的个股深研 Agent 流程，理论上可以设计一套独立、轻量、快速的选股专用回测系统，不必绑定第 1 点里那套重量级的多 Agent 决策回测。

**待厘清的开放问题**

- akshare 财报接口滞后的 bug 修复方案和影响面评估，需要单独排期，且要先确认哪些下游模块（`shared_data_access`、`factor_store`、`quant_prefilter`）会被这个时间口径改动波及。
- 独立选股回测系统与第 1、3 点的回测框架是否要共享同一套底层设施（数据接口、交易日历、净值计算），还是完全独立成一套更简单的框架？

## 5. 记忆系统的设计

**现状问题**

当前记忆机制很简单：把每只股票的历史决策 JSON 追加写入研究包末尾，并主动剔除 `recommended_action` 和 `price_impression` 字段，防止这些历史结论直接带偏下一日决策（参见 `.codex/skills/auto-trading-fixed-tracked/references/`、`configs/prompt_flow/fixed_tracked/stock_analysis_policy.md` 中「持仓与投资逻辑记忆」一节）。这只解决了"不要机械照抄历史动作"的问题，还远不够。

**改进方向（待讨论，非结论）**

- 需要设计一套金融领域专用的记忆系统，让下一日的交易 AI 能够继承对每只股票过去决策的完整上下文，而不只是一份被裁剪过的 JSON 片段。
- 同时需要一种**反思机制**：能根据股票后续实际走势，回头验证过去的决策判断是否正确、是否合理，从而形成"决策 → 结果 → 反思纠偏"的闭环，而不是让错误的历史记忆持续带偏后续判断。

**待厘清的开放问题**

- 反思机制由谁执行、多久触发一次（每日、每次深度分析、还是财报验证时）？反思结论以什么形式沉淀（打分、文本复盘、调整某个置信度参数）？
- 反思结论如何影响下一轮分析，同时又不违反当前"不能把旧的 `recommended_action`/`price_impression` 当作当天直接指令"的既有约束？这两者需要有清晰的边界。
- 记忆系统的数据结构是否要和第 6 点的数据存储/组织模式改造一起设计，避免先做一套后面又要迁移。

---

## 6. 数据存储和组织模式

**现状问题**

当前为了最快实现功能，数据组织方式很简单（大量 JSON/Markdown 文件散落在 `data/` 目录下的各级子目录中）。

**改进方向**

- 参考部分开源项目（如 DojoAgents）的数据组织方式，评估哪些设计可以吸收进当前项目。
- 后续目标是把数据存储统一切换到 SQL（关系型数据库），取代目前分散的文件式存储。

**待厘清的开放问题**

- 迁移范围：是只迁移新增数据（记忆系统、benchmark），还是要把 `data/agent_data/`、`data/skill_runs/`、`data/stock_info/` 这些现有文件式产物也迁移？全量迁移对现有 `01-08` 产物契约和 `shared_data_access` 缓存注册机制影响很大，需要谨慎评估迁移路径和过渡期兼容方案。
- 与 DojoAgents 等参考项目的具体对照分析（哪些设计好、好在哪、如何适配到本项目的多账本/多 Agent 场景）还没有做，需要单独调研。

## 7. 界面的设计

**优先级最低**，主要目的是提升易用性，不影响当前核心分析和回测能力。暂不展开设计，留待前面几项有阶段性进展后再排期。
