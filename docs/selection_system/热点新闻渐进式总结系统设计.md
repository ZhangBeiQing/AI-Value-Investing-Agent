# 热点新闻渐进式总结系统设计

更新日期：2026-03-18

说明：

1. 本文档专门描述 `merge-hot-news-state` 的详细设计。
2. 目标不是做“今日新闻摘要”，而是做一个面向交易叙事的渐进式主题状态系统。
3. 本文档是 `docs/selection_system/AI选股系统一期落地设计.md` 中 `Step 2. merge-hot-news-state` 的详细展开。

## 1. 设计目标

`merge-hot-news-state` 的本质应是：

1. 一个小型主题数据库的日更调度器。
2. 默认倾向归档与丢弃，而不是默认保留。
3. 只有在新证据到来时才更新旧主题。
4. 严禁同一叙事每天重新命名、重新建主题。

它解决的问题不是：

1. “今天有哪些新闻值得看”。
2. “把今天的热点重新总结一遍”。

它真正解决的问题是：

1. 昨天市场在交易哪些主题。
2. 今天新增新闻让哪些旧主题被强化、弱化或证伪。
3. 哪些新叙事值得升级成新主题。
4. 哪些旧叙事已经应该退出主上下文。

## 2. 上游输入链路

`hot_news_state` 的直接上游是新闻链的 `03_news_enriched.json`。

当前新闻链建议理解为：

```text
Step 1. run-news
  01_news_candidates.json
    -> 新闻候选采集
  02_news_dedup_decisions.json / 02_news_deduped.json
    -> DeepSeek 去重与筛噪
  03_news_enriched.json
    -> 对保留新闻打开链接、抽取正文、补足结构化字段
```

其中 `03_news_enriched.json` 的作用是：

1. 为主题系统提供当天较高保真的新闻正文与元数据。
2. 为后续板块研究和选股模型提供新闻事实底稿。
3. 作为“今天新增证据”的唯一主输入，而不是直接输出交易主题。

新闻链负责：

1. 候选新闻采集。
2. 去重与筛噪。
3. 正文增强。

新闻链不负责：

1. 主题增量更新。
2. 主题归档与遗忘。
3. 板块轮动研究。
4. 最终选股结论。

## 3. 为什么不做成纯 Skill

最初设想是把 `merge-hot-news-state` 做成一个 `SKILL.md` workflow，让模型按步骤执行。

当前更合适的落地方向是：

1. 核心逻辑做成代码服务。
2. workflow 只做外壳与编排说明。

原因：

1. 这是一个状态机，而不是单次生成任务。
2. 其中很多步骤适合确定性代码执行，不适合每次重新让模型自由发挥。
3. 后续需要反复调参数、做回放、加测试、看日志，代码形态更容易维护。

推荐形态：

1. `services/selection_system/hot_news_state.py`
   - 负责主流程编排、召回、操作计划、状态落盘。
2. `services/selection_system/hot_news_theme_matcher.py`
   - 负责主题匹配、相似主题召回、merge 判定。
3. `services/selection_system/hot_news_store.py`
   - 负责 SQLite 状态库与 JSON 产物同步。
4. `services/selection_system/hot_news_llm.py`
   - 负责 prompt 组装、模型调用、结果解析与重试。
5. `workflow / skill`
   - 只保留“入口命令、输入输出、排障方式”的薄外壳。

## 4. 存储设计

推荐采用：

1. `SQLite` 作为内部状态库。
2. `JSON` 作为外部产物格式。

也就是：

1. 对内：便于增量更新、归档、召回、调试、回放。
2. 对外：继续输出 `data/selection_runs/YYYY-MM-DD/06_hot_news_state.json`，保持链路清晰。

不建议一期直接上重型数据库。原因：

1. 当前数据规模不大。
2. SQLite 足够支持主题、证据、操作日志、历史状态。
3. 一期重点是状态逻辑与可解释性，不是分布式扩展。

### 4.1 建议落盘

```text
data/
  market_state/
    hot_news_state/
      latest.json
      YYYY-MM-DD.json
      hot_news_state.db
```

### 4.2 SQLite 建议表

1. `themes`
   - 主题主表
2. `theme_daily_state`
   - 每日快照
3. `theme_evidence`
   - 主题与新闻证据关联
4. `theme_operations`
   - 每次更新的操作日志
5. `theme_aliases`
   - 主题别名、旧名、可检索标签

## 5. 总体流程

建议把 `merge-hot-news-state` 拆成四段：

```text
1. extract-news-theme-candidates
   -> 从 03_news_enriched.json 抽取今日主题候选

2. retrieve-relevant-old-themes
   -> 从旧状态中召回当前活跃/冷却/命中的归档主题

3. plan-theme-ops
   -> 让模型只输出操作，不直接重写整份 hot_news_state

4. apply-theme-ops
   -> 用 Python 确定性生成今日 hot_news_state 与操作日志
```

### 5.1 Step A：抽取今日主题候选

输入：

1. 今日 `03_news_enriched.json`

输出：

1. `theme_candidates`

每个 candidate 建议包含：

1. 候选主题名
2. 主题一句话定义
3. 直接证据新闻 ID
4. 提及的核心实体
5. 涉及行业/板块
6. 候选置信度

注意：

1. 这一步只做“从新闻中看到了哪些叙事候选”。
2. 不做旧主题更新。
3. 不做归档。

### 5.2 Step B：召回相关旧主题

输入：

1. `theme_candidates`
2. 旧状态中的 `active` / `cooling` / `archived`

输出：

1. 对每个 candidate，给出若干个 `matched_old_theme_candidates`

召回方式建议采用 hybrid：

1. 规则召回
   - 主题名精确匹配
   - 别名匹配
   - 板块名、行业名、核心实体命中
2. embedding 召回
   - 从旧主题 summary / aliases / evidence 摘要中检索语义相近项
3. 召回结果裁剪
   - 每个 candidate 只保留少量最相关旧主题，避免上下文爆炸

embedding 模型建议：

1. 优先接阿里云 `text-embedding-v4`
2. embedding 只用于召回与候选排序
3. 最终“是不是同一主题”不应只靠 embedding 阈值单独决定

### 5.3 Step C：计划主题操作

这一步是核心。

模型只允许输出操作，不允许直接重写完整状态。

建议的操作集：

1. `ADD_THEME`
2. `UPDATE_THEME`
3. `MERGE_THEME`
4. `ARCHIVE_THEME`
5. `DROP_CANDIDATE`
6. `NOOP`

说明：

1. `ADD_THEME`
   - 确认是全新主题，且无法合理匹配到旧主题。
2. `UPDATE_THEME`
   - 今日 candidate 与某个旧主题是同一主题，只是在新增证据。
3. `MERGE_THEME`
   - 两个旧主题本质上已被证明是同一交易叙事，应合并。
4. `ARCHIVE_THEME`
   - 旧主题缺乏新证据，或已明显退潮，应退出主上下文。
5. `DROP_CANDIDATE`
   - 今日 candidate 只是噪声，不足以升级为主题。
6. `NOOP`
   - 既不新建，也不更新，也不触发归档动作。

### 5.4 Step D：确定性应用操作

这一步由 Python 完成，不交给模型自由生成。

主要职责：

1. 更新 `theme_id` 与时间字段
2. 写入证据新闻 ID
3. 维护 active/cooling/archived 状态迁移
4. 写入 `theme_operations`
5. 生成 `06_hot_news_state.json`

这样做的好处：

1. 可回放
2. 可调试
3. 可测试
4. 不会因为模型格式漂移把状态写坏

## 6. “同一主题”与 “merge” 不是完全同一个问题

这两个问题强相关，但不完全相同。

### 6.1 什么叫“同一主题”

“同一主题”是：

1. 今日 candidate 是否应更新某个已有主题。

这是一个：

1. `candidate -> existing_theme`
2. 的匹配问题。

### 6.2 什么时候允许 merge 两个主题

“merge”是：

1. 两个已经存在的主题，是否应该在状态库中合并成一个主题。

这是一个：

1. `existing_theme_a <-> existing_theme_b`
2. 的整库整理问题。

所以：

1. `same theme` 更偏“新增候选和旧主题的匹配”
2. `merge theme` 更偏“旧主题之间是否冗余或别名化”

两者使用相似的匹配能力，但触发条件不一样。

## 7. 如何判断“同一主题”

不建议用单一规则。

建议采用三层判断：

1. 规则硬约束
2. embedding 候选召回
3. LLM 最终裁决

### 7.1 规则硬约束

先过滤掉明显不可能是同一主题的组合。

可用特征：

1. 核心实体是否重叠
2. 板块/行业是否明显相关
3. 主题关键词是否包含上下位词、别名或常见同义表达
4. 时间窗口是否连续

例如：

1. `稀土涨价` 与 `有色金属`
   - 不应默认视为同一主题
   - `有色金属` 是更宽的板块或行业框
   - `稀土涨价` 是更具体的交易叙事
2. `军工订单` 与 `军贸出口`
   - 很可能属于同一条更具体的军工外需/订单强化叙事
   - 应进入同主题候选或 merge 候选池，不能直接按字面分开

### 7.2 embedding 召回

对每个今日 candidate，计算与旧主题的语义相似度。

embedding 输入建议使用组合文本：

1. `canonical_theme_name`
2. `summary`
3. `aliases`
4. 最近若干条关键证据新闻标题
5. 关联板块与核心实体摘要

embedding 的作用：

1. 找到“字面不同但语义接近”的旧主题
2. 给 LLM 裁决前缩小候选集合

embedding 不应该单独决定：

1. 是否一定同一主题
2. 是否一定 merge

原因：

1. 它擅长召回，不擅长精确解释交易叙事边界
2. 市场主题有大量上下位词、板块词、催化词，纯向量很容易过宽

### 7.3 LLM 最终裁决

模型对候选 pair 做分类：

1. `same_theme`
2. `mergeable`
3. `distinct`

建议不要只有二分类。

原因：

1. `same_theme`
   - 今天 candidate 应直接更新旧主题
2. `mergeable`
   - 当前还不是严格同一命名，但两个旧主题长期看应并为一个主主题
3. `distinct`
   - 保持分开

### 7.4 推荐判定逻辑

#### `same_theme`

满足以下倾向时可判定：

1. 核心叙事一致
2. 主要实体/板块高度重叠
3. 今日证据只是旧叙事的延续、强化、分化或证伪
4. 若更新后主题名不需要本质改写

#### `mergeable`

满足以下倾向时可判定：

1. 两个主题长期看描述的是同一个交易主线
2. 只是此前命名角度不同
3. 近几天证据、板块、龙头、催化已经高度重合
4. 合并后信息增益大于信息损失

#### `distinct`

满足以下倾向时保持分开：

1. 主题虽然处在同一板块，但催化链条不同
2. 同一大行业下的不同交易分支
3. 合并后会把细分交易逻辑压扁

## 8. 什么时候允许 merge 两个主题

merge 不应是高频动作，而应是保守动作。

建议只有在以下情形同时出现时才允许：

1. 两个主题已连续多日共享大部分证据或证据方向
2. 关联板块、龙头、核心实体高度重合
3. 二者之间主要差异只是命名口径，而不是逻辑差异
4. merge 后不会丢失交易上重要的细分信息

### 8.1 不建议 merge 的情况

1. 大板块词与细分催化词
   - 如 `有色金属` 与 `稀土涨价`
2. 同一行业下的不同驱动
   - 如 `AI 算力扩容` 与 `AI 应用落地`
3. 同一军工板块内，但一个是内需订单，一个是军贸出口，且证据链明显不同

### 8.2 建议 merge 的情况

1. 只是不同命名角度
   - 如 `军贸出口` 与 `军工外需订单`
2. 一个是旧简称，一个是新规范名
3. 多天运行后发现两个主题反复被同一批新闻、同一批板块、同一批龙头支撑

## 9. 主题状态机

建议最少维护以下状态：

1. `candidate`
2. `active`
3. `cooling`
4. `archived`

### 9.1 含义

1. `candidate`
   - 今日刚抽取出来，尚未确认是否升级为主题
2. `active`
   - 处于主上下文中，后续选股模型可直接看到
3. `cooling`
   - 仍保留，但已经不再是当前主线
4. `archived`
   - 退出主上下文，默认不进入明日 prompt，除非被新新闻命中召回

### 9.2 遗忘原则

默认命运应是：

1. `candidate -> drop`
2. `active -> cooling -> archived`

而不是：

1. 主题一旦出现就长期留在主上下文里

## 10. 上下文控制

推荐只给模型看有限的 working set，而不是全量历史主题。

每日 merge 时的 prompt 上下文建议只包含：

1. 当前 `active` 主题
2. 最近若干个 `cooling` 主题
3. 今日 candidate 命中的 `archived` 主题
4. 今日 `03_news_enriched.json` 中进入候选的新闻

不命中的历史归档主题不要进入 prompt。

这相当于借鉴 MemOS 的：

1. working memory replacement
2. unrelated filtering
3. redundancy filtering
4. rerank

但对热点主题系统做了更激进的遗忘化改造。

## 11. 借鉴 MemOS 的部分

MemOS 中最值得借鉴给本系统的思路：

1. 不直接重写整份状态，而是先输出操作。
2. 更新前先召回相关旧对象，而不是把全量历史都塞进 prompt。
3. 对 `UPDATE` 做额外安全校验。
4. 使用归档、working set 替换、冗余过滤，而不是简单暴力删除。

不直接照搬的部分：

1. MemOS 默认偏向“保留长期记忆”
2. 热点主题系统必须默认偏向“快速衰减与归档”

## 12. 推荐一期实现边界

一期建议先实现：

1. SQLite 状态库
2. 主题 candidate 抽取
3. hybrid 召回
4. `ADD_THEME / UPDATE_THEME / MERGE_THEME / ARCHIVE_THEME / DROP_CANDIDATE`
5. `06_hot_news_state.json`
6. 详细操作日志

一期先不强求：

1. 复杂图数据库
2. 过度自动化的主题本体体系
3. 非常复杂的跨主题推理

## 13. 待继续细化的问题

虽然大方向已确定，但后续仍需继续迭代：

1. `hot_news_state` 最终 JSON 字段契约
2. SQLite 表结构与索引
3. theme candidate 抽取 prompt
4. theme ops 计划 prompt
5. `same_theme / mergeable / distinct` 的阈值与回测口径
6. 不同类型主题的半衰期参数
7. 如何把板块热度层反向用作主题持续性的证据

## 14. 当前结论

当前建议已经明确：

1. `merge-hot-news-state` 以代码服务为主，而不是纯 Skill。
2. 相似主题匹配采用 `规则 + embedding + LLM裁决` 的混合方案。
3. “同一主题”与“merge”相关但不完全相同，不能混成一个布尔判断。
4. 默认要让系统学会归档与遗忘，而不是不断累积主题。
5. 外部继续保留 `06_hot_news_state.json`，内部采用 SQLite 便于增量维护与测试。
