# 热点新闻渐进式总结系统设计

更新日期：2026-04-03

说明：

1. 本文档描述新的 `gradual-hot-news-summary` 设计目标与产物结构。
2. 目标不是做“今日新闻摘要”，而是做一个可被后续本地选股 agent 直接继承的“主题级研究记忆”。
3. 本文档替代旧版偏“最小状态机”的设计表述，保留其增量更新思想，但把输出重心从“简短状态标签”升级为“可交接的主题脉络”。

## 1. 为什么需要这个系统

这个系统的作用，不是把新闻尽可能多地抓下来，也不是把新闻直接挂靠到每只股票上。

它真正解决的问题是：

1. 昨天市场在交易哪些主题。
2. 今天新增新闻让哪些旧主题被强化、弱化、证伪或切换。
3. 哪些主题已经被板块资金确认，哪些只是文字层噪声。
4. 哪些主题值得驱动 agent 去股票宇宙外补搜索新的标的。
5. 如何把这些“叙事级上下文”交给一个明天才上线的全新 agent。

因此它在整个选股系统中的定位是：

1. `macro_summary` 负责“世界观 / 大类资产框架”。
2. `hot_news_gradual_summary` 负责“可交易叙事的演化记忆”。
3. `board_heat_state` 负责“板块与资金确认”。
4. `stock_snapshot_payload` 负责“个股事实层与估值层”。

一句话说：

`macro_summary` 解决“为什么世界在变化”，  
`hot_news_gradual_summary` 解决“今天该重点交易什么叙事”，  
`board_heat_state` 解决“市场到底有没有在交易这个叙事”，  
`snapshot` 解决“具体买哪只股票”。

## 2. 它和宏观总结、板块热点、个股 snapshot 的边界

### 2.1 与宏观总结的关系

会共享一部分事实，但职责不同。

宏观总结应保留：

1. 利率、美元、黄金、原油、央行、战争、关税、增长/通胀框架。
2. 对 A 股 / 港股 / 黄金 / 石油 / 美股的顶层映射。

渐进式新闻总结应保留：

1. 哪些宏观变化已经转化为可交易主题。
2. 这些主题今天比昨天发生了什么变化。
3. 这些主题和哪些板块、哪些股票候选相关。

因此：

1. 宏观总结负责“顶层框架”。
2. 渐进式新闻总结负责“中观叙事状态”。

### 2.2 与板块热点模块的关系

板块热点模块是“盘面验证层”。

它告诉 agent：

1. 哪些板块今天真的强。
2. 强度是否在扩散、分化、还是集中于龙头。
3. 某个新闻叙事有没有被市场真实交易。

因此：

1. 渐进式新闻总结负责“叙事是什么、怎么演化”。
2. 板块热点模块负责“这个叙事有没有被市场确认”。

### 2.3 与个股 snapshot 的关系

个股 snapshot 负责：

1. 估值
2. 质量
3. 财报
4. 风险
5. 经营与技术状态

因此：

1. 渐进式新闻总结不直接替代个股研究。
2. 它只负责把 agent 的注意力引导到更值得研究的主题和股票候选。

## 3. 是否保留这个功能

结论：应保留，而且应升级为核心能力。

原因：

1. 仅靠宏观总结太高层，离最终选股还差一层“交易叙事桥梁”。
2. 仅靠板块热点太盘面，缺少“这条线过去几天为什么成立、未来怎么证伪”的解释。
3. 仅靠股票 snapshot 太个股，无法提供跨股票、跨板块、跨叙事的统一背景。
4. 未来你希望一个全新的本地 agent 只读“今天的输入”就能工作，那就必须把主题的过去、现在和未来线索写进当天的主题总结里。

因此，这个系统不应该弱化成“主题标签列表”，而应该升级成：

`主题级可继承研究记忆系统`

## 4. 执行形态：本地 skill + 本地 agent

旧设计里把它更多视为代码服务。

新设计建议调整为：

1. 保留必要的本地代码与缓存能力。
2. 把执行入口收敛到 `.codex/skills/` 下的专门 skill。
3. 由本地 agent 负责主题级总结、补充联网核验和输出组织。

建议的用户触发方式：

1. 用户说“更新今天的渐进式新闻总结”
2. skill 启动
3. 本地 agent 执行固定流程

### 4.1 skill 的标准步骤

1. `source /home/zhangbeiqing/venv/ai_stock/bin/activate`
2. 运行本地代码生成当天新闻链产物，至少拿到 `03_news_enriched.json`
3. 读取最近一天的历史渐进式主题总结
4. 以“今天新闻 + 昨日主题状态”为主输入，执行主题增量总结
5. 若某些最新事件在 `03_news_enriched.json` 中信息不足，但对主题判断关键，则允许 agent 自行联网搜索补证
6. 产出今日新的渐进式主题总结

### 4.2 agent 的核心输入

默认主输入只有两个：

1. 今日整理好的新闻正文输入
2. 最近一天的历史主题总结

允许的补充输入：

1. 宏观总结
2. 板块热点状态
3. 必要时的联网补证结果

但第一版不应强依赖大量额外输入，否则 skill 会过重。

## 5. 上游新闻输入文件设计

当前 `03_news_enriched.json` 适合做原始事实层，但不适合直接完整塞进 agent prompt。

建议新增一个轻量输入文件，例如：

`03_news_prompt_input.json`

只保留对主题总结真正需要的字段：

```json
{
  "news_id": "B001",
  "title": "李强到四川调研",
  "published_at": "2026-04-02T06:00:04",
  "source": "em_breakfast",
  "content": "..."
}
```

不进入 prompt 的字段包括：

1. `content_fetch_status`
2. `fetch_error`
3. `url`

原因：

1. 这些字段对 agent 判断主题帮助很小。
2. 保留它们会浪费 token。
3. 原始完整版仍可落盘给调试和回放使用。

因此建议保留双层：

1. `03_news_enriched.json`
   - 完整落盘，便于调试
2. `03_news_prompt_input.json`
   - 轻量输入，便于主题 skill 消费

## 6. 为什么不把新闻直接挂到股票宇宙上

不建议把“新闻挂靠在 300 只股票上”作为主设计。

更好的主路径仍然是：

`宏观 -> 主题 -> 板块 -> 股票`

原因：

1. 新闻天然先影响主题和板块，再传导到股票。
2. 直接挂股票会造成大量冗余复制。
3. 会限制 agent 的视野，让它只在既有股票宇宙中思考。
4. 未来若要做宇宙外扩，主题层是最自然的触发点。

可以保留一个派生层：

1. 由主题映射到股票
2. 给股票打“主题暴露标签”
3. 作为 snapshot 或排序模块的补充输入

但它不应替代主题层本身。

## 7. 新的输出目标

输出不再只是：

1. `theme_name`
2. `status`
3. `summary`

而应当让一个明天才上线的 agent，仅仅读到今天的 JSON，也能理解：

1. 这个主题为什么进入主上下文
2. 它过去几天怎么发展到今天
3. 今天发生了什么新增变化
4. 当前市场到底在交易这个主题的什么部分
5. 明天还要继续跟踪什么
6. 它关联哪些宏观主题、板块和股票
7. 是否值得扩展股票宇宙

## 9. 主题字段说明

### 9.1 `history_anchor`

用途：

1. 提供一个新 agent 直接继承的历史锚点。
2. 说明这个主题为什么值得长期保留在上下文里。

应包含：

1. 主题最初进入主上下文的原因
2. 最近几天最关键的变化链
3. 当前判断的历史依据

### 9.2 `today_update`

用途：

1. 只描述今天相对昨天新增了什么

应包含：

1. 关键新闻
2. 新表态
3. 关键事件
4. 资金或板块层面的新确认

### 9.3 `current_state`

用途：

1. 把“历史锚点 + 今日变化”压缩成当前状态结论

应回答：

1. 市场今天到底在交易这个主题的什么部分
2. 这条线是强化、分化、衰减还是等待确认

### 9.4 `forward_paths`

用途：

1. 描述未来 1-5 个交易日可能出现的主要演化路径
2. 帮助后续 agent 理解“这个主题不是确定性的，而是有条件分支的”

注意：

1. 不是宏观长周期预测
2. 只写和选股、板块、市场风格相关的近端路径
3. 不能只写单向乐观路径，必须同时覆盖延续、钝化、反转等主要分支

### 9.5 `expected_duration`

用途：

1. 提醒 agent 这条主题已经持续了多久
2. 帮助判断它目前处于“刚启动 / 中段强化 / 高位拥挤 / 退潮前夜”的哪个阶段

建议包含：

1. `already_running_for`
2. `base_case`
3. `decay_signals`

### 9.6 `scenario_tree`

用途：

1. 把主题未来的主要情景分支结构化
2. 防止 agent 把 `active_theme` 错当成确定性结论

建议每个情景包含：

1. `scenario`
2. `probability_band`
3. `trigger_signals`
4. `market_impact`

概率写法建议：

1. 使用 `high / medium / low / low_to_medium / medium_to_high`
2. 或使用粗区间，如 `20-40%`
3. 不建议写过度精确的点概率

### 9.7 `key_risks`

用途：

1. 显式提醒后续 agent：这个主题可能如何被证伪、降温或反转
2. 防止 agent 因为看到 `active_theme` 就过度确信

建议保留：

1. 会直接改变主题方向的风险
2. 会导致板块先于新闻反转的交易风险
3. 会导致股票选择发生明显切换的结构风险

### 9.8 `next_day_watchlist`

用途：

1. 为明天的新 agent 提供明确跟踪清单

要求：

1. 尽量具体
2. 可执行
3. 可被搜索或核验

## 10. `key_events` 设计

你提出的担心是正确的：

如果一个主题持续一个月，相关事件可能几百条，不能全部挂进主题里。

因此建议：

1. `key_events` 不是全量新闻列表
2. 它是 agent 选出来的“重要节点链”
3. 应兼顾重要程度和时间顺序

### 10.1 设计原则

1. 每个主题只保留少量高价值事件节点
2. 优先保留改变主题方向的节点
3. 优先保留第一次进入主上下文的起点事件
4. 优先保留从“强化 -> 分化 -> 衰减 -> 再强化”的拐点事件
5. 若某个主题已持续很久，优先保留能解释阶段切换的重要节点，而不是平均抽样

### 10.2 建议上限

每个主题最多挂靠：

1. `30-50` 个 key events

进一步建议：

1. `active` 主题默认保留最近 `20-30` 个最重要节点
2. 只有极少数超长主线主题才允许扩到 `50`

### 10.3 选择规则

应由 agent 自动选择，而不是机械保留每天全部新闻。

优先级建议：

1. `critical`
   - 方向性切换节点
2. `high`
   - 强化或证伪的重要确认
3. `medium`
   - 补足事件链连续性的关键背景

不应保留：

1. 重复表态
2. 无新增事实的跟风报道
3. 不改变叙事方向的细碎噪声

### 10.4 `key_events` 与高层摘要的关系

分工应是：

1. `key_events`
   - 保留原始事件链骨架
2. `history_anchor`
   - 对历史主线做压缩总结
3. `today_update`
   - 对当日增量做压缩总结
4. `current_state`
   - 给出今天的高层状态结论
5. `scenario_tree`
   - 给出未来的主要分支推演
6. `key_risks`
   - 给出主题失效或反转的提醒

也就是说：

1. `key_events` 是原始证据骨架
2. 上层字段是面向新 agent 的解释层
3. `scenario_tree` 和 `key_risks` 用来抑制单向叙事偏见

## 11. 主题是否允许联网补证

允许，而且应作为正式设计的一部分。

原则：

1. 默认先依赖本地 `03_news_prompt_input.json`
2. 若本地新闻只给了短摘要，但某个主题今天显著变化且摘要信息不足，则允许 agent 联网补证

适用场景：

1. 战争、关税、制裁、央行、产业政策这类事件
2. 对主题方向判断影响大的高权重事件
3. 板块或股票宇宙扩展时所需的代表股核验

不建议联网补证的场景：

1. 普通低价值公司新闻
2. 只影响单一个股、对主题无外溢的日常公告

## 12. 哪些新闻应该进入这个系统

应进入主主题系统的内容：

1. 会改变市场叙事的宏观、政策、产业、地缘新闻
2. 会驱动板块或赛道重估的行业级事件
3. 少量对板块或市场有外溢性的公司事件

不应进入主主题系统的内容：

1. 普通财报
2. 小额担保
3. 常规减持、增持
4. 对板块和市场没有扩散意义的日常公告

对于这类单公司信息，更适合进入：

1. 个股 snapshot
2. 股票侧观察清单
3. 股票侧决策日志

## 13. 主题如何映射到股票

主题层不直接负责最终选股，但必须提供股票映射线索。

建议至少输出：

1. `linked_symbols_in_universe`
2. `outside_universe_names_to_check`
3. `search_trigger`

作用：

1. 帮助 agent 在宇宙内优先看哪些股票
2. 触发 agent 在宇宙外搜索新的龙头或弹性股

因此它是：

1. 主题 -> 板块 -> 股票
2. 的桥梁层

## 15. 推荐一期实现边界

一期建议先实现：

1. 轻量新闻输入文件 `03_news_prompt_input.json`
2. 本地 skill 入口
3. 主题级输出结构
4. `history_anchor / today_update / current_state / forward_paths / next_day_watchlist`
5. 有上限的 `key_events`
6. `linked_boards / linked_symbols_in_universe / outside_universe_names_to_check / search_trigger`
7. 必要时联网补证

一期先不强求：

1. 复杂图数据库
2. 股票级新闻全量挂靠
3. 过度细的主题本体体系

## 16. 当前结论

当前建议已经明确：

1. 这个功能应该保留，并升级为核心能力。
2. 它不再只是“主题状态机”，而应是“主题级可继承研究记忆”。
3. 主题输出必须能让一个全新的 agent 直接继承昨天的判断锚点。
4. `key_events` 必须是有限上限的“重要节点链”，而不是全量新闻堆积。
5. 执行入口应逐步收敛为 `.codex/skills/` 下的本地 skill。
6. 原始新闻文件和 prompt 输入文件应分层，减少 token 浪费。
7. 主题层应成为 `宏观 -> 板块 -> 股票` 之间的中间桥梁，并承担宇宙外扩的触发职责。
